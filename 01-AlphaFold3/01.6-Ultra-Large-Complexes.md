(af3-ultra-large)=
Modeling ultra-large complexes with AlphaFold3 (AF3) can be challenging due to the significant computational resources required, particularly GPU memory. As the size and complexity of the complex increase, so do the demands on GPU memory, which can lead to out-of-memory errors if not properly managed.

When preparing to run AF3 jobs for ultra-large complexes on CHTC, consider the following factors.

(af3-gpu-considerations)=
## Key AF3 GPU Considerations

Token count drives GPU memory needs:

* **Tokens ≈ 1.2 × total sequence length across all chains**
* **RNA/DNA bases count as tokens**
* **Larger complexes need more GPU memory**

Typical GPU memory guidelines:

| Tokens     | Estimated GPU Memory Requirement |
|------------|----------------------------------|
| Up to 1200 | 8-10 GB                          |
| 1200-1850  | 15-20 GB                         |
| 2000-3000  | 35-40 GB                         |
| Over 3000  | 70+ GB                           |

Unified memory:

* For very large complexes (>10k tokens)
* Significantly slower
* Increase `request_memory` when enabling `--enable_unified_memory` in your executable arguments

If you would like to learn more about CHTC's GPU capacity, visit the [GPU Guide on the CHTC Documentation Portal](https://chtc.cs.wisc.edu/uw-research-computing/gpu-jobs).

## Running Using Unified Memory

Unified memory mode allows AlphaFold3 to use both GPU memory and system RAM, which can be particularly useful for modeling ultra-large (>10k tokens) complexes that exceed the available GPU memory. However, using unified memory can lead to **significantly slower performance**. When using unified memory mode, you must also ensure that the execute point has sufficient system RAM to support the additional memory requirements. This means increasing the `request_memory` attribute in your HTCondor submit file to accommodate the larger memory footprint.

Unified memory mode is enabled by adding the `--enable_unified_memory` flag to your executable arguments. This instructs AlphaFold3 to use unified memory during inference, allowing it to handle larger models that would otherwise exceed GPU memory limits.

When using unified memory mode, monitor the performance of your jobs closely, as the increased data transfer between system RAM and GPU memory leads to longer execution times. If you encounter out-of-memory errors even with unified memory enabled, consider further increasing the `request_memory` attribute in your submit file or reaching out to the CHTC Research Computing Facilitation team for assistance.

### Unified Memory Example

To enable unified memory mode in your AlphaFold3 inference jobs, add the `--enable_unified_memory` flag to the `arguments` attribute of your submit file and increase `request_memory` so the execute point has enough system RAM. Here is an example submit file for unified memory mode, derived from the `inference_pipeline.sub` used in [Step 2](./01.5-Running-Inference.md):

```{code} bash
:filename: inference_pipeline.sub
:linenos:
:emphasize-lines: 22,27,29,33
# CHTC maintained container for AlphaFold3
container_image = osdf:///osg-public/containers/alphafold3-custom-v6.sif

executable = scripts/inference_pipeline.sh

environment = "myjobdir=$(my_directory)"

MODEL_WEIGHTS_PATH = /staging/<netid>/tutorial-CHTC-AF3/af3.bin.zst

log = ./logs/inference_pipeline.log
output = inference_pipeline_$(Cluster)_$(Process).out
error  = inference_pipeline_$(Cluster)_$(Process).err

initialdir = AF3_Jobs/$(my_directory)
transfer_input_files = inference_inputs/, osdf:///chtc/$(MODEL_WEIGHTS_PATH)
transfer_output_files = inference_pipeline.tar.gz
transfer_output_remaps = "inference_pipeline.tar.gz=$(my_directory).inference_pipeline.tar.gz"

should_transfer_files = YES
when_to_transfer_output = ON_EXIT

request_memory = 600GB
request_disk = 10GB
request_cpus = 4
request_gpus = 1

gpus_minimum_memory = 139 GB

+GPUJobLength = "long"
+WantGPULab = true
+is_alphafold3 = true

arguments = --model_param_file af3.bin.zst --work_dir_ext $(Cluster)_$(Process) --enable_unified_memory

queue my_directory from list_of_af3_jobs.txt
```

:::{hint} Unified Memory Job Submission Considerations
When using unified memory mode, ensure that the execute point has sufficient system RAM to support the additional memory requirements. In the example above, the `request_memory` attribute (line 22) is set to 600 GB, which may need to be increased depending on the size of the complex being modeled. Estimating the required system RAM can be challenging, but as a general guideline, allocate at least 4-6 times the estimated GPU memory requirement for your complex. For example, if your complex is estimated to require 100 GB of GPU memory, request at least 400-600 GB of system RAM. Some complexes require even more, so monitor your job performance and adjust the memory request as needed.

Unified memory jobs can be significantly slower. Therefore, flag your jobs as long-running by setting `+GPUJobLength = "long"` (line 29) in your submit file, which allows the job to run for a maximum of 7 days. Long-running jobs are not suited to backfill slots, so **omit `+is_resumable = true` and `want_ospool = true`** from your submit file to avoid preemption.

Finally, add the `--enable_unified_memory` flag to the `arguments` attribute (line 33). This flag instructs AlphaFold3 to use unified memory during inference, allowing it to handle larger models that would otherwise exceed GPU memory limits. The example also targets a large-memory GPU with `gpus_minimum_memory = 139 GB` (line 27).
:::

## Running Ultra-Large Complexes

AlphaFold3 is able to model very large complexes, but doing so requires careful consideration of GPU memory requirements and performance trade-offs. You can model ultra-large complexes on CHTC by enabling unified memory mode and adjusting your resource requests accordingly.

### Adjusting Memory Pre-Allocation

For ultra-large complexes, you may also need to adjust the JAX GPU memory pre-allocation settings to better manage memory usage. By default, JAX pre-allocates 95% of GPU memory, which may not be sufficient for very large models. You can modify this behavior using the `--mem_preallocation_fraction` flag in your executable arguments.

When using unified memory mode, JAX attempts to pre-allocate 3.2x the GPU's total memory (tapping into system RAM as needed) by setting `XLA_CLIENT_MEM_FRACTION=3.2`. Most of the time, this is enough to run large complexes (>10k tokens). However, if you encounter out-of-memory errors, you can increase this value further. In such cases, consider setting it to values like 5.0 or 10.0 to allow JAX to use more system RAM alongside GPU memory.

Include this flag in your executable arguments as follows:

```{code} bash
:filename: inference_pipeline.sub
:linenos:
:emphasize-lines: 22,27,33
# CHTC maintained container for AlphaFold3
container_image = osdf:///osg-public/containers/alphafold3-custom-v6.sif

executable = scripts/inference_pipeline.sh

environment = "myjobdir=$(my_directory)"

MODEL_WEIGHTS_PATH = /staging/<netid>/tutorial-CHTC-AF3/af3.bin.zst

log = ./logs/inference_pipeline.log
output = inference_pipeline_$(Cluster)_$(Process).out
error  = inference_pipeline_$(Cluster)_$(Process).err

initialdir = AF3_Jobs/$(my_directory)
transfer_input_files = inference_inputs/, osdf:///chtc/$(MODEL_WEIGHTS_PATH)
transfer_output_files = inference_pipeline.tar.gz
transfer_output_remaps = "inference_pipeline.tar.gz=$(my_directory).inference_pipeline.tar.gz"

should_transfer_files = YES
when_to_transfer_output = ON_EXIT

request_memory = 1250GB
request_disk = 10GB
request_cpus = 4
request_gpus = 1

gpus_minimum_memory = 139 GB

+GPUJobLength = "long"
+WantGPULab = true
+is_alphafold3 = true

arguments = --model_param_file af3.bin.zst --work_dir_ext $(Cluster)_$(Process) --enable_unified_memory --mem_preallocation_fraction 8.0

queue my_directory from list_of_af3_jobs.txt
```

:::{hint} Adjusting Memory Pre-Allocation for Ultra-Large Complexes
The JAX environment variable `XLA_CLIENT_MEM_FRACTION` controls the fraction of GPU memory that JAX pre-allocates. It also functions as a multiplier when using unified memory mode. By default, JAX pre-allocates 95% of GPU memory, which may not be sufficient for ultra-large complexes.

In the example above, the job targets a GPU with at least 139 GB of memory (line 27) using the `gpus_minimum_memory` HTCondor attribute. The `--mem_preallocation_fraction 8.0` argument (line 33) instructs JAX to pre-allocate 8 times the GPU's total memory when the job starts. This means the execute point needs at least 1.1 TB of system RAM (139 GB of GPU memory × 8.0) available to accommodate this pre-allocation, so `request_memory` (line 22) is set to 1250 GB.
:::

### Additional Considerations

Ultra-large complexes may require significant computational resources and longer execution times. They are also more susceptible to performance issues, such as out-of-memory errors or interruptions due to system outages.

To mitigate these risks, consider the following strategies:

* **Resource monitoring:** monitor resource usage closely during job execution to identify potential bottlenecks or performance issues, and adjust resource requests based on observed usage.
* **Consultation with CHTC staff:** for particularly large or complex modeling tasks, consult the CHTC Research Computing Facilitation team for guidance on optimizing job configurations and resource allocations.
* **Longer job durations:** be prepared for longer job durations when modeling ultra-large complexes, especially when using unified memory mode. Set `+GPUJobLength = "long"` so your jobs may run for extended periods.
* **Testing with smaller models:** before running ultra-large complexes, test your job configuration with smaller models to confirm that your setup is working. This can surface problems before you commit significant resources.
* **Community resources:** engage with the broader AlphaFold3 user community to share experiences and learn from others who have modeled ultra-large complexes.

:::{warning} Memory Fragmentation Issues with Ultra-Large Complexes
A known problem with running ultra-large complexes on CHTC is memory fragmentation on the execute points. Memory fragmentation occurs when free memory is divided into small, non-contiguous blocks, making it difficult to allocate the large contiguous blocks required by applications such as AlphaFold3. This is a common occurrence on shared computing resources like CHTC, where multiple jobs may be running simultaneously on the same machine. It can lead to situations where, despite sufficient total memory, the job fails because it cannot allocate a contiguous block of the required size. Jobs affected by memory fragmentation typically fail with out-of-memory errors early in the JAX memory pre-allocation phase, even though total memory usage is below the requested amount.
