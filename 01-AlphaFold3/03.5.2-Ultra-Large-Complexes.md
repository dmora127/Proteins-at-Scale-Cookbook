Modeling ultra-large protein complexes with AlphaFold3 (AF3) can be challenging due to the significant computational resources required, particularly in terms of GPU memory. As the size and complexity of the protein complex increase, so do the demands on GPU memory, which can lead to out-of-memory errors if not properly managed.

When preparing to run AF3 jobs for ultra-large complexes on CHTC, it is essential to consider the following factors:

# Key AF3 GPU considerations:

Token count drives GPU memory needs
* **Tokens ≈ ~1.2 × total sequence length across all chains**
* **RNA/DNA bases count as tokens**
* **Larger complexes → more GPU memory**
Typical GPU memory guidelines:
* | Tokens     | Estimated GPU Memory Requirement |
  |------------|----------------------------------|
  | Up to 1200 | 8-10 GB                          |
  | 1200-1850  | 15-20 GB                         |
  | 2000-3000  | 35-40 GB                         |
  | Over 3000  | 70+ GB                           |

* **Unified memory:**
  * Very large complexes (>10k tokens)
  * Significantly slower
  * Increase `request_memory` if enabling `--enable_unified_memory` in your executable arguments

If you would like to learn more about our GPU capacity, please visit our [GPU Guide on CHTC Documentation Portal](https://chtc.cs.wisc.edu/uw-research-computing/gpu-jobs).

# Running Using Unified Memory

Unified memory mode allows AlphaFold3 to utilize both GPU memory and system RAM, which can be particularly useful for modeling ultra-large (>10k tokens) complexes that exceed the available GPU memory. However, it is important to note that using unified memory can lead to **significantly slower performance**. When using unified memory mode, you should also ensure that the execute node has sufficient system RAM to support the additional memory requirements. This may involve increasing the `request_memory` attribute in your HTCondor submit file to accommodate the larger memory footprint.

Unified memory mode can be enabled by adding the `--enable_unified_memory` flag to your executable script arguments. This instructs AlphaFold3 to utilize unified memory during inference, allowing it to handle larger models that would otherwise exceed GPU memory limits.

When using unified memory mode, it is recommended to monitor the performance of your jobs closely, as the increased data transfer between system RAM and GPU memory can lead to longer execution times. If you encounter out-of-memory errors even with unified memory enabled, consider further increasing the `request_memory` attribute in your submit file or reaching out to the CHTC Research Computing Facilitation team for assistance.


## Unified Memory Example

To enable unified memory mode in your AlphaFold3 inference jobs, you can modify your HTCondor submit file to include the `--enable_unified_memory` flag in the `arguments` attribute of your job submission. Additionally, you should increase the `request_memory` attribute to ensure that the execute node has enough system RAM to support the larger memory requirements.

Here is an example of how to set up your submit file for unified memory mode:

```{code} bash
:filename: run_dorado.sh
:linenos:
:emphasize-lines: 20, 27, 30,
# CHTC maintained container for AlphaFold3 as of December 2025
container_image = file:///staging/groups/glbrc_alphafold/af3/alphafold3.minimal.22Jan2025.sif

executable = inference_pipeline.sh

environment = "myjobdir=$(directory)"

MODEL_WEIGHTS_PATH = /staging/damorales4/af3/weights/af3.bin.zst

log = ../logs/inference_pipeline.log
output = inference_pipeline_$(Cluster)_$(Process).out
error  = inference_pipeline_$(Cluster)_$(Process).err

initialdir = $(directory)
transfer_input_files = inference_inputs/, $(MODEL_WEIGHTS_PATH)

should_transfer_files = YES
when_to_transfer_output = ON_EXIT

request_memory = 600GB
request_disk = 10GB
request_cpus = 4
request_gpus = 1

gpus_minimum_memory = 13900

+GPUJobLength = "long"
+WantGPULab = true

arguments = --model_param_file af3.bin.zst --work_dir_ext $(Cluster)_$(Process) --enable_unified_memory 

queue directory from list_of_af3_jobs.txt
```

:::{hint} Unified Memory Job Submission Considerations
When using unified memory mode, it is important to ensure that the execute node has sufficient system RAM to support the additional memory requirements. In the example above, the `request_memory` attribute (line 20) is set to 600GB, which may need to be increased depending on the size of the protein complex being modeled. Estimating the required system RAM can be challenging, but as a general guideline, you may want to allocate at least 4-6 times the estimated GPU memory requirement for your complex. For example, if your complex is estimated to require 100GB of GPU memory, you should consider requesting at least 400-600GB of system RAM. Some complexes may require even more, so it is advisable to monitor your job performance and adjust the memory request as needed.

Unified memory jobs can be significantly slower. Therefore, it is recommended to flag your jobs as long-running by setting the `+GPUJobLength` attribute to `"long"` (line 27) in your submit file. This will allow your job to run for a maximum of 7 days. These long-running jobs are not optimized for running on backfill slots, so it is important to **exclude `+is_resumable = true` from your submit file** to avoid potential issues with job preemption.

Beyond adjusting the `request_memory` attribute, you should also ensure that your executable script includes the `--enable_unified_memory` flag in the `arguments` attribute (line 30). This flag instructs AlphaFold3 to utilize unified memory during inference, allowing it to handle larger models that would otherwise exceed GPU memory limits.
:::

# Running Ultra-Large Complexes

AlphaFold3 is able to model very large protein complexes, but doing so requires careful consideration of GPU memory requirements and potential performance trade-offs. You can model ultra-large complexes on CHTC by enabling unified memory mode and adjusting your resource requests accordingly.

## Adjusting Memory Pre-Allocation
For ultra-large complexes, you may also need to adjust the JAX GPU memory pre-allocation settings to better manage memory usage. By default, JAX pre-allocates 95% of GPU memory, which may not be sufficient for very large models. You can modify this behavior using the `--mem_preallocation_fraction` flag in your executable script.

When using unified memory mode, JAX will attempt to pre-allocate 3.2x the GPU's total memory (tapping into system RAM as needed) by setting `XLA_CLIENT_MEM_FRACTION=3.2`. Most times, this is enough to running large complexes (>10k tokens). However, if you encounter out-of-memory errors, you can increase this value further. In such cases, consider setting it to values like 5.0 or 10.0 to allow JAX to utilize more system RAM alongside GPU memory. 

You can include this flag in your executable script as follows:

```{code} bash
:filename: run_dorado.sh
:linenos:
:emphasize-lines: 20, 25, 30,
# CHTC maintained container for AlphaFold3 as of December 2025
container_image = file:///staging/groups/glbrc_alphafold/af3/alphafold3.minimal.22Jan2025.sif

executable = inference_pipeline.sh

environment = "myjobdir=$(directory)"

MODEL_WEIGHTS_PATH = /staging/damorales4/af3/weights/af3.bin.zst

log = ../logs/inference_pipeline.log
output = inference_pipeline_$(Cluster)_$(Process).out
error  = inference_pipeline_$(Cluster)_$(Process).err

initialdir = $(directory)
transfer_input_files = inference_inputs/, $(MODEL_WEIGHTS_PATH)

should_transfer_files = YES
when_to_transfer_output = ON_EXIT

request_memory = 1250GB
request_disk = 10GB
request_cpus = 4
request_gpus = 1

gpus_minimum_memory = 13900 

+GPUJobLength = "long"
+WantGPULab = true

arguments = --model_param_file af3.bin.zst --work_dir_ext $(Cluster)_$(Process) --enable_unified_memory --mem_preallocation_fraction 8.0

queue directory from list_of_af3_jobs.txt
```

:::{hint} Adjusting Memory Pre-Allocation for Ultra-Large Complexes
The JAX environment variable `XLA_CLIENT_MEM_FRACTION` controls the fraction of GPU memory that JAX pre-allocates. It also functions as a multiplier when using unified memory mode. By default, JAX pre-allocates 95% of GPU memory, which may not be sufficient for ultra-large complexes. 

In the example above, our job will be targeted to a GPU with at least 139 GB of memory (line 25) using the `gpus_minimum_memory` HTCondor attribute. We are instructing JAX to pre-allocate 8 times the GPU's total memory when the job starts (line 30) using the CLI argument `--mem_preallocation_fraction 8.0`. This means we will need at least 1.1 TB of system RAM (139 GB of vRAM x 8.0 of JAX multiplier) available on the execute node to accommodate this pre-allocation. We must ensure that our `request_memory` attribute (line 20) is set to at least 1200GB to provide sufficient system RAM for the job.
:::

## Additional Considerations

Ultra-large complexes may require significant computational resources and longer execution times. They are also more susceptible to various performance issues, such as out-of-memory errors or interruptions due to system outages. 

To mitigate these risks, consider the following strategies:
* **Resource Monitoring:** Monitor resource usage closely during job execution to identify potential bottlenecks or performance issues. Adjust resource requests as needed based on observed usage patterns.
* **Consultation with CHTC Staff:** For particularly large or complex modeling tasks, consider consulting with the CHTC Research Computing Facilitation team. They can provide guidance on optimizing job configurations and resource allocations for ultra-large complexes.
* **Longer Job Durations:** Be prepared for longer job durations when modeling ultra-large complexes, especially when using unified memory mode. Ensure that your jobs are configured to run for extended periods by setting the `+GPUJobLength` attribute to `"long"` in your submit file.
* **Testing with Smaller Models:** Before running ultra-large complexes, consider testing your job configurations with smaller models to ensure that your setup is functioning correctly. This can help identify potential issues before committing significant resources to larger tasks.
* **Community Resources:** Engage with the broader AlphaFold3 user community to share experiences and learn from others who have successfully modeled ultra-large complexes. Online forums, user groups, and research collaborations can provide valuable insights and support.

:::{warning} Memory Fragmentation Issues with Ultra-Large Complexes
A known problem with running ultra-large complexes on CHTC is the potential for memory fragmentation on the execute nodes. Memory fragmentation occurs when free memory is divided into small, non-contiguous (one-after-another) blocks, making it difficult to allocate large contiguous blocks of memory required for certain applications, such as AlphaFold3. This is a common occurance on shared computing resources like CHTC, where multiple jobs may be running simultaneously on the same machine. This can lead to situations where, despite having sufficient total memory available, the job fails due to the inability to allocate a contiguous block of memory required for the model. The typical behavior for jobs affected by memory fragmentation is to fail with out-of-memory errors, even when the total memory usage is below the requested amount, early during the memory pre-allocation phase of JAX.
