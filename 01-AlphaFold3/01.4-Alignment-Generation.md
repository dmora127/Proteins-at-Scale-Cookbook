(af3-data-pipeline)=
The data-pipeline stage prepares all alignments, templates, and features needed for AF3 prediction. These CPU-only jobs run on CHTC's standard compute nodes and can be scaled to many sequences at once. In the steps below, you will submit one data-pipeline job per sequence, producing the feature tarballs required for the GPU inference stage. This step requires a large (~750 GB) database set, which has been pre-staged on certain CHTC execute points; see [AlphaFold3 Databases on CHTC](#af3-databases) for how to make the most of it.

## Review the Data Pipeline Executable

1. Change to your `tutorial-CHTC-AF3/` directory:

   ```bash
   cd ~/tutorial-CHTC-AF3/
   ```

2. Review the data pipeline executable script `scripts/data_pipeline.sh`:

   ```bash
   cat scripts/data_pipeline.sh
   ```

   For this tutorial, no changes are necessary. When you are ready to run your own jobs, review the overview below, as your AF3 jobs may require additional non-default options.

### Overview: AlphaFold3 Data Pipeline Executable (Data-Only Stage)

This script implements the **data-generation portion** of the AlphaFold3 workflow, the part that creates alignments, MSA features, and template features required for structure prediction. It **does not run the structure inference** step. It is designed for execution inside HTCondor jobs on CHTC systems and supports both containerized and pre-staged database workflows.

The script handles:

- Preparing a clean per-job working directory
- Detecting database availability (local `/alphafold3` vs. copying from staging)
- Copying and/or binding input JSON files
- Running the AlphaFold3 **data pipeline only**
- Tarballing the resulting `data_pipeline` outputs for transfer back to the Access Point
- Cleaning up the job sandbox to minimize disk use

#### 1. Checking for Pre-Staged AF3 Databases

CHTC hosts a copy of the AlphaFold3 databases locally on certain machines. Machines with these databases advertise this resource using the `HasAlphafold3` HTCondor machine attribute. The script can run on machines with or without these databases pre-loaded. It inspects the job's `.machine.ad` file to see whether the matched machine advertises the databases:

```bash
HasAlphafold3 = true
```

The script also checks that the `/alphafold3/` path is not empty. If the attribute is `true` **and** `/alphafold3/` is populated, the script uses the pre-extracted AF3 databases; otherwise it falls back to decompressing databases locally in the job's scratch space.

The databases hosted by CHTC include the full AF3 default database suite:

- PDB mmCIF
- MGnify clusters
- UniRef90
- UniProt (full database)
- BFD first non-consensus sequences
- RNAcentral
- NT RNA clusters
- Rfam

Databases may be updated periodically by CHTC staff. If you require a custom database set (e.g., reduced-size databases for testing), you can modify the script to use your own database tarballs. Contact the [CHTC Research Computing Facilitation team](https://chtc.cs.wisc.edu/uw-research-computing/get-help.html) for assistance.

#### 3. Working Directory Setup

Creates:

```bash
work.<ext>/
    af_input/
    af_output/
    models/
    public_databases/
    tmp/
```

and moves all `*.json` files into `af_input/`.

#### 4. Running the AlphaFold3 Data Pipeline

Inside the container:

```bash
python run_alphafold.py --run_data_pipeline=true --run_inference=false
```

This generates all alignment and feature files under `af_output/<job_name>/`.

#### 5. Packaging Results

Each output directory is archived as `data_pipeline.tar.gz` and returned to the Access Point, where the submit file renames it to `<job>.data_pipeline.tar.gz` inside the job's `inference_inputs/` directory.

### MSA CPU and Worker Settings

The data pipeline uses HMMER-based searches to generate alignments. The `data_pipeline.sh` wrapper exposes two options that control how much CPU parallelism each data-pipeline job uses:

- `--msa_cpus_per_worker <N>` controls how many CPUs each individual Jackhmmer/Nhmmer search may use. The default is `1`.
- `--msa_workers <N>` controls how many MSA searches may run at the same time. If this option is not provided, the wrapper uses `PYTHON_CPU_COUNT` when it is available, otherwise it defaults to `1`.

The approximate CPU demand of the MSA stage is:

```text
estimated MSA CPU use = msa_cpus_per_worker × msa_workers
```

For high throughput, we generally recommend keeping `--msa_cpus_per_worker 1` and scaling with `--msa_workers`. For example, a 4-core data-pipeline job should usually run as `--msa_cpus_per_worker 1 --msa_workers 4`, rather than `--msa_cpus_per_worker 4 --msa_workers 1`. This keeps each HMMER process simple to account for while still allowing multiple independent database searches to run concurrently.

When the estimated MSA CPU use is `1`, the wrapper prints a warning to both stdout and stderr that the job is running in single-core mode. This is valid and often useful for high-throughput runs, but expect longer per-job runtimes.

#### Choosing Data-Pipeline CPU Settings

The best CPU setting depends on whether you want shorter runtimes for each individual job or higher overall throughput across many jobs.

| Goal | `request_cpus` | Recommended wrapper arguments | Notes |
|------|----------------|-------------------------------|-------|
| Maximum matchability / many independent jobs | `1` | `--msa_cpus_per_worker 1 --msa_workers 1` | Slowest per job, but easiest to match. Expect substantially longer runtimes. |
| Balanced default | `2` | `--msa_cpus_per_worker 1 --msa_workers 2` | Good compromise for many production runs. |
| Faster per-job runtime on pre-staged database nodes | `4` | `--msa_cpus_per_worker 1 --msa_workers 4` | Runs multiple database searches concurrently. Recommended when database I/O is local and stable. |
| Single search using multiple CPUs | `4` | `--msa_cpus_per_worker 4 --msa_workers 1` | Useful when you want to avoid multiple simultaneous database scans, but usually not the preferred default. |

Do not set `--msa_cpus_per_worker × --msa_workers` higher than `request_cpus`. For example, if `request_cpus = 4`, avoid `--msa_cpus_per_worker 4 --msa_workers 4`, because that creates roughly 16 CPUs worth of MSA demand inside a 4-CPU allocation.

(af3-msa-cache)=
### MSA Caching and Reuse

The data pipeline's main output is a feature bundle that includes MSAs and templates. If you have multiple jobs with shared sequences (e.g., the same protein with different ligands), you can reuse the same MSA outputs across those jobs to save time and resources. Across a community of users, many protein chains, protein families, organisms, and benchmark inputs are searched repeatedly. To support reuse of these precomputed alignments, the Partnership to Advance Throughput Computing (PATh) maintains an alignment library and caching mechanism.

The alignment library reduces duplicated work by allowing precomputed alignments to be reused when the sequence, source, and provenance are appropriate for your workflow:

- **Faster cache-aware runs**: jobs that find an acceptable cached MSA can skip part or all of the repeated sequence-search stage for that chain.
- **Lower CPU and storage pressure**: repeated database searches are replaced with OSDF/Pelican reads of smaller alignment artifacts.
- **Reproducibility and provenance**: cached records include source and checksum metadata so you can distinguish generated, imported, and community-contributed alignments.
- **Community reuse**: every validated contribution can make later structure-prediction workflows faster for other researchers.

To use this feature, pass the `--use-cached-msa` flag to the `data_pipeline.sh` wrapper, together with an API key (`--cache_api_key`). The wrapper then checks the alignment library for existing MSAs that match the input sequence and search parameters before performing new database searches. You can also pass `--cache_preferred_sources` with an ordered list of sources to prefer; if it is omitted, the wrapper uses the default order (OSG-Generated, Google DeepMind, Community Contributed, Others). Available sources include `OSG-Generated`, `Google DeepMind`, `Community Contributed`, `Nvidia`, `BFVD`, `Viro3D`, `AllTheBacteria`, and `Kinetoplastid`.

:::{tip} Getting an API key, and contributing your alignments
To request an API key for the alignment library, email [chtc@cs.wisc.edu](mailto:chtc@cs.wisc.edu). Data pipeline jobs run with `--use-cached-msa` automatically contribute their generated MSAs to the library, along with provenance metadata. To contribute alignments from earlier runs, contact the PATh team at [support@osg-htc.org](mailto:support@osg-htc.org). Learn more in the [PATh alignment library documentation](https://osg-htc.org/services/osdf/alphafold).
:::

## Prepare Your Data Pipeline Jobs

3. Review the submit file `data_pipeline.sub` in the top level of the repository. It works out of the box if you set up your job directories as described in [Setting Up AlphaFold3 Input JSONs and Job Directories](#af3-job-directories). You can pass additional options to the executable through the `arguments` attribute as needed; see the [command-line options](#af3-data-pipeline-options) above.

   ```{code} bash
   :filename: data_pipeline.sub
   :linenos:
   :emphasize-lines: 3,11,16,23,38
   # CHTC maintained container for AlphaFold3
   # Can use the local CHTC copy at file:///staging/groups/chtc_staff/containers/alphafold3.minimal.22Jan2025.sif
   container_image = osdf:///osg-public/containers/alphafold3-custom-v6.sif

   executable = scripts/data_pipeline.sh

   log = ./logs/data_pipeline.log
   output = data_pipeline_$(Cluster)_$(Process).out
   error  = data_pipeline_$(Cluster)_$(Process).err

   initialdir = AF3_Jobs/$(my_directory)
   transfer_input_files = data_inputs/

   # transfer output files back to the submit node
   transfer_output_files = data_pipeline.tar.gz
   transfer_output_remaps = "data_pipeline.tar.gz=inference_inputs/$(my_directory).data_pipeline.tar.gz"

   should_transfer_files = YES
   when_to_transfer_output = ON_EXIT
   keep_claim_idle = 1800
   on_exit_hold = (ExitCode != 0)
   on_exit_hold_reason = "Non-zero Exit Code - Check Error and Output files."

   # We need this to transfer the databases to the execute node
   Requirements = (Target.HasCHTCStaging == true) && (TARGET.HasAlphafold3 == true)

   # We use this condition for internal logic and reporting, please do not remove.
   +is_alphafold3 = true

   if defined USE_SMALL_DB
     # testing requirements
     request_memory = 8GB
     request_disk = 16GB
     request_cpus = 4
     arguments = --smalldb --work_dir_ext $(Cluster)_$(Process) --verbose
   else
     # full requirements
     request_memory = 24GB
     # Request less disk if matched machine already has AF3 DB preloaded (650GB savings); values are in KiB
     request_disk = 700000000 - ( (TARGET.HasAlphafold3?: 1) * 650000000)
     request_cpus = 8
     arguments = "--work_dir_ext $(Cluster)_$(Process) --cache_api_key <API_KEY> --use-cached-msa --msa_cpus_per_worker 1 --cache_preferred_sources 'Community Contributed - Cached, OSG-Generated'"
   endif

   queue my_directory from list_of_af3_jobs.txt
   ```

   :::{attention} No alignment-library API key yet?
   The full-database `arguments` line (line 41) opts into the MSA cache and needs an API key in place of `<API_KEY>`. If you do not have a key, shorten the line to `arguments = --work_dir_ext $(Cluster)_$(Process) --msa_cpus_per_worker 1`; the pipeline then searches the databases directly.
   :::

   This submit file reads the contents of `list_of_af3_jobs.txt`, iterates through each line, and assigns the value of each line to the variable `$(my_directory)`. This lets you programmatically submit _N_ jobs, where _N_ equals the number of AlphaFold3 job directories you created. Each job runs in its own job directory (`initialdir`, line 11), processes that directory's `data_inputs/`, and uses the CHTC-maintained AlphaFold3 container image (line 3), which HTCondor transfers to the Execution Point (EP) through OSDF.

   The output tarball `data_pipeline.tar.gz` is returned to the Access Point and renamed into the job's `inference_inputs/` directory (line 16), ready for Step 2. Jobs that exit with a non-zero code are placed on hold so you can inspect their `.out` and `.err` files. `keep_claim_idle` lets the next queued job reuse a matched machine (and its pre-staged databases) without waiting for a new match.

   The `Requirements` line (line 23) matches only machines that advertise the `HasAlphafold3` attribute, so the pre-staged databases are available locally. You can remove the `&& (TARGET.HasAlphafold3 == true)` clause to run on machines with and without pre-staged databases: this increases the number of available machines, leading to faster _start_ times, but jobs that land elsewhere copy and extract the databases first, which can add well over 45 minutes to the runtime. The `request_disk` expression (line 38) requests roughly 50 GB when the matched machine advertises the databases and roughly 700 GB otherwise.

   In the full-database branch, each job requests 8 CPUs and passes `--msa_cpus_per_worker 1`, so each MSA search uses a single CPU and up to eight searches run concurrently. For maximum matchability, you can instead request one CPU and run with `--msa_workers 1`; this single-core mode is slower per job but may allow more jobs to run at once.

   :::{attention} Memory Considerations for Highly Conserved Sequences and Deep Alignments
   AlphaFold3 jobs can be resource-intensive, especially with highly conserved query sequences. Conserved sequences can generate very deep alignments, which may require significantly more memory. If you encounter out-of-memory errors during job execution, increase the `request_memory` attribute in your submit file. You can also use the `retry_request_memory = <memory/expression>` command to retry automatically with more memory if a job is held for an out-of-memory error. For more information, visit the CHTC [Request variable memory](https://chtc.cs.wisc.edu/uw-research-computing/variable-memory#use-retry_request_memory) guide.
   :::

(af3-databases)=
## AlphaFold3 Databases on CHTC

CHTC maintains a full, pre-extracted copy of the AlphaFold3 reference databases on a subset of execute points. When your data-pipeline jobs match to one of these machines, they use the local `/alphafold3` directory directly, avoiding the costly transfer and extraction of several hundred gigabytes of database files. This dramatically reduces startup time, disk requirements, and overall job runtime. If a job lands on a machine without pre-staged databases, the script automatically falls back to unpacking the databases in the job's scratch space, so every job can run regardless of where it matches.

You target the pre-staged database nodes with `requirements = (TARGET.HasAlphafold3 == true)`, as shown in the submit file above. After the job has matched, `data_pipeline.sh` also checks the matched machine's attributes and uses the local databases when they are present.

## Submit and Monitor Your Data Pipeline Jobs

4. Submit your data-pipeline jobs from the top level of the repository:

   ```bash
   condor_submit data_pipeline.sub
   ```

   :::{hint} Testing with Reduced-Size Databases
   You can test the data pipeline using reduced-size databases by defining the `USE_SMALL_DB=1` variable when submitting your jobs. This is useful for debugging and testing, as it reduces resource requirements and speeds up job execution:

   ```bash
   condor_submit USE_SMALL_DB=1 data_pipeline.sub
   ```
   :::

5. Track your job progress:

   ```bash
   condor_watch_q
   ```

   When a job finishes, its `inference_inputs/` directory contains `<job>.data_pipeline.tar.gz`, the input for [Step 2](#af3-inference-pipeline).
